# BHS Computing Science Platform

## Overview
This project is an educational web platform for Biggar High School's Computing Science department. It provides interactive learning materials and tools for various computing science courses (National 5, Higher, Games Development, Cyber Security), aiming to enhance student engagement and understanding. Key capabilities include a Higher CS Revision App, interactive widgets, an AI quiz system, and specialized tools like a Paper Builder, Data Sculptor, and code editors with cloud synchronization. The platform seeks to be a comprehensive and interactive resource for students and teachers.

## User Preferences
Preferred communication style: Simple, everyday language.

## System Architecture

### Frontend Architecture
The platform features a multi-page static website with a responsive, mobile-first design using vanilla CSS. It includes dynamic sidebar navigation, image optimization, interactive educational widgets, content search, and an accessibility panel. Code blocks have syntax highlighting, and interactive Python/HTML/CSS code runners are implemented using Pyodide and srcdoc iframes.
Separate React + TypeScript Single Page Applications (SPAs) are used for revision apps (`/revision/`, `/revision-n5/`), the BHS Classwork app (`/classwork/`), and the Data Sculptor (`/data-sculptor/`). These SPAs offer student accounts, teacher dashboards, AI marking, class management, and sandboxed database environments with Access-style design views. Code editor tools include personal project dashboards with local and cloud saving, and auto-save functionality.

### Backend Architecture
A Node.js/Express server, built with TypeScript, serves static content and provides CRUD API endpoints for content management and code projects. Security measures include blocking sensitive file access, implementing security headers, and disabling Express fingerprinting. A unified database schema manages student and class data, with content tables shared across course levels. Authentication uses Bearer tokens for students and email/password for teachers, with unified logins and cross-app settings synchronization via localStorage. The BHS Classwork app integrates AI marking for various question types (text, multiple-choice, code, link, file-upload, presentation, video), supporting manual override and re-marking. It also includes features for managing student classes (move/copy, archive, rename) and lesson resources (images, documents, YouTube, links, embeds) with robust CRUD operations. Visual marking for presentations is optionally supported using LibreOffice and Gemini Vision.

### Core Features
- **Higher/N5 CS Revision Apps:** React SPAs with student accounts, teacher dashboards, AI marking, and assignment tracking. Both `QuestionEditor` Preview dialogs include a **"Try as student"** dry-run: every sub-question (and nested sub-part) with `maxMarks > 0` gets a cyan-bordered panel containing a textarea, an `ImagePasteInput` when `inputStyle === "image-paste"` (pre-loads `drawingBackgroundUrl` as the starter), and a **Get AI feedback** button that POSTs to the existing stateless `/api/grade-answer` endpoint (no DB writes, no auth required) and renders marks / bullet feedback / suggestions inline. Local state (`previewAnswers`, `previewImages`, `previewFeedback`) is reset whenever the dialog closes. Higher sends `{ studentAnswer, markingScheme, maxMarks, questionContext, aiGuidance, referenceFiles, studentDiagramImage }`; N5 sends `{ studentAnswer, markingScheme, maxMarks, questionContext, aiGuidance, markingGuidanceData, diagramImage }` — matching the field shapes the student-facing `Revision.tsx` uses. Diagram-style answers use a single unified `image-paste` input: students draw their answer in any external app, paste the image into a shared `ImagePasteInput` (clipboard / drag-drop / file picker, auto-downscaled, stored as a base64 PNG/JPEG data URL in `inputs["diagram_image"]`). Teachers can attach an optional **Starting image** via `subQ.drawingBackgroundUrl`; when set, students get a **Copy starting image** button that uses the `ClipboardItem` API so they can paste a labelled diagram into their drawing tool, annotate it, then paste the result back. Grading is multimodal: the N5 server (`server/n5-routes.ts`) attaches the pasted base64 to the Gemini call when `inputStyle === "image-paste"`; the Higher server (`server/revision-routes.ts`) receives the image as `studentDiagramImage` in the `/api/grade-answer` body. All legacy diagram-editor styles (`drawing`, `erd-annotation`, `nav-structure`, `nav-structure-higher`, `tag-matching`, `structure-dataflow`, `form-wireframe`, `webpage-wireframe`, `structure-diagram`, `entity-occurrence-diagram`) have been migrated in place to `image-paste` (backups in `questions_diagram_backup_20260424` / `n5_questions_diagram_backup_20260424`); the legacy `DiagramEditor` component is no longer wired into student renderers but its `DiagramItem` type is still imported as `type-only` for de-serialising historic stored answers in review/analytics screens.
- **Paper Builder:** Teacher tool for creating, editing, and managing exam papers, questions, and assignments.
- **Data Sculptor:** Sandboxed database tool with personal multi-database dashboards and advanced database design capabilities for teachers, including AI marking for SQL tasks.
- **Code Editor Project Dashboards:** Personal project management for Python and HTML/CSS editors with cloud synchronization.
- **Classwork view-tracking + auto-saved drafts:** Pupils' lesson pages report which question cards have actually scrolled into view (`POST /api/classwork/questions/:questionId/view`, fired once per page-load by an `IntersectionObserver` on each `[data-classwork-question-id]` card at a 30% threshold) and auto-save in-progress answers (`PUT/DELETE /api/classwork/questions/:questionId/draft`, debounced ~1.2 s after each input change, force-flushed via `fetch({ keepalive: true })` on `pagehide`/`visibilitychange:hidden`/`StudentAnswer` unmount). Drafts are bulk-loaded for a lesson via `GET /api/classwork/lessons/:lessonId/my-drafts` in the same `Promise.all` as `my-submissions`. The server uses two new raw-SQL tables created inside `ensureClassworkSchema()` (no Drizzle): `bhs_classwork_question_views (PK student_id+question_id; first_viewed_at, last_viewed_at, view_count)` and `bhs_classwork_drafts (PK student_id+question_id; text_answer, selected_option_label, link_url, file_url, updated_at)` — both with `VARCHAR(64)` IDs matching every other `bhs_classwork_*` table. `createSubmission()` deletes the matching draft row so a real submission always wins. Auto-save covers `short`, `long`, `code`, `multiple_choice`, `video_question`, `sql_task`, `scratch_link`, `makecode_link`, `google_sites_link`, `screenshot`, `project`, `presentation`, `fill_in_blanks`, `table`, `labeled_inputs` — code-editor tasks (`python_task`/`html_task`) and `database_task` are skipped because they have their own per-project / sandbox persistence. The teacher Analytics drill-down's per-question table gains an **"Opened"** column (driven by `getLessonAnalytics` LEFT JOINing the views table for `distinct_viewers`) so teachers can distinguish "couldn't access" from "opened but didn't finish". `StudentAnswer` shows a small `Saving… / Draft saved / Couldn't save draft` pill next to the Submit button so pupils have visible reassurance that their work is safe.
- **BHS Classwork App:** A React SPA for AI-marked classwork across multiple year levels. It includes comprehensive teacher tools for class and student management (move, copy, archive, rename), lesson editing (learning intentions, success criteria), per-unit thumbnails (each `bhs_classwork_units` row carries an optional `image_url TEXT` — added via the same additive `ALTER TABLE ... ADD COLUMN IF NOT EXISTS` pattern used for other classwork columns; teachers set it from the New unit / Edit unit modals on `Course.tsx`, either by pasting a URL or uploading an image through the existing `/api/classwork/teacher/upload/resource` endpoint via the shared `UnitImageField` helper; the `Course.tsx` `UnitThumb` component renders it as a 56px rounded square to the left of the unit title — falling back to a soft gradient initial-letter tile when no image is set so every row stays vertically aligned), and per-question resource attachment (images, documents, YouTube, links, embeds; the legacy lesson-level resource panel has been retired — every resource now lives on a specific question). Supports various question types, including specific integrations for Python, HTML, and SQL tasks, and introduces "extension activity" flagging. Also supports general-purpose types ported from the revision apps: **info_only** (non-interactive note, no answer area, no marks, hidden from analytics), **section_header** (visual divider that groups the questions below it — no marks, no answer area, no resources panel; rendered as a slate-grey banner with an accent left border; question numbering continues across sections so analytics keyed off `question_id` are unaffected; excluded from all analytics `NOT IN` clauses alongside `passage`/`info_only`), **text_only** (offline task: pupils do the work in their jotter — writing, sketches, screenshots — with no digital answer collected; rendered with a cyan-tinted card, a "Task" label instead of a Q-number, and a dashed-border callout containing an "Open my jotter" button; `noAnswerType` in the editor `save()` zeros marks/scheme/AI-guidance and the editor hides those fields; excluded from `markSubmission` in `server/classwork-ai.ts` and from all 7 analytics `NOT IN ('passage','info_only','section_header','text_only')` clauses in `server/classwork-storage.ts`), **fill_in_blanks** (prompt with `{{id}}` placeholders rendered as inline inputs; config: `{ blanks: [{ id, accept: [...] }] }`), **table** (a 2D grid where teachers mark cells as fixed text or blank-with-accepted-answers; config: `{ table: { headers: [...], rows: [[{ value } | { blank: true, accept: [...] }]] } }`), and **labeled_inputs** (multiple labelled fields per question; config: `{ fields: [{ label, accept: [...] }] }`). All three are marked in `server/classwork-ai.ts` via a shared `gradeCellList` engine: each cell is either exact-match (case- and whitespace-insensitive against `accept[]`) or AI-judged (teacher writes a per-cell `aiGuidance` note instead of an accept list — all such cells in one submission are batched into a single Gemini call returning `{ <cellKey>: { correct, feedback } }`). Final mark is scaled `correct/total * max_marks`; pupils submit a JSON object in `text_answer` keyed by blank id / `"r,c"` / field index. The Analytics page has a **Download Excel** button that calls a teacher-only `GET /api/classwork/:course/analytics/export.xlsx` endpoint (in `server/classwork-export.ts`, dynamically imported, built with `exceljs`) returning a multi-sheet workbook (Overview, Lessons, Students, Questions, Lesson scores) with frozen headers, navy header styling, and green data-bar conditional formatting on every "Average %" / "Percent" column so each cell renders as a built-in horizontal bar chart. Native Excel chart objects are not generated (exceljs doesn't write them) — teachers can use Excel's *Insert → Chart* on the formatted tables for further pivots.
- **Per-student activity calendar:** The Analytics page's `StudentDetail` panel renders a small monthly calendar (Mon-start, prev/next nav, capped at the last 12 months) that highlights every day the pupil did *anything* in the course. Driven by a teacher-only `GET /api/classwork/:course/students/:studentId/activity-days` endpoint that returns `{ days: ["YYYY-MM-DD", ...] }` derived in a single SQL `UNION ALL` of existing timestamp columns: `bhs_classwork_submissions.submitted_at`, `bhs_classwork_question_views.first_viewed_at` / `last_viewed_at`, and `bhs_classwork_drafts.updated_at` (each filtered by `course = $1 AND student_id = $2 AND ts >= NOW() - INTERVAL '12 months'`). No new schema or write paths — it's purely a derived read. The component shows "X active days this month · Y in the last 12 months" beneath the grid, treats today as a bordered cell, and dims future dates. Mounted unconditionally so a teacher sees the engagement view even before the pupil has submitted anything (opening any lesson card already counts as activity via the existing `bhs_classwork_question_views` IntersectionObserver).
- **BHS Progress Tracker:** A unified SPA for teachers to view student progress across all courses.
- **Site-Wide Student Login:** A vanilla-JS component for consistent student authentication across the main site and SPAs.

### Testing
- **Vitest** with **@testing-library/react** and **jsdom** are used for regression tests. Tests live under `tests/` (per-app subfolders: `tests/n5/`, `tests/revision/`, `tests/ds/`) and run via `npm test`. Each app has its own Vitest project so the `@/` alias resolves to the correct client source folder. Current coverage focuses on render-loop regressions in the diagram editor (n5 + revision), `AccessDesignCanvas`, and `DataGrid`, asserting that unstable parent callbacks and re-renders never cause runaway effects (React error #185).
